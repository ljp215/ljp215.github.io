据 CNBC 报道，英伟达首席财务官科莱特·克雷斯（Colette Kress）在黄仁勋突然辞职后出任临时 CEO。 克雷斯 2013 年 9 月加入英伟达，此前在思科、微软和德州仪器担任财务职务，并长期与黄仁勋一同出席财报电话会。

英伟达的接班问题由“创始人之下没有明确二号人物”转为公开的临时安排，后续观察点是正式继任者来自内部还是外部。

Runway 模型/产品发布 基础模型与技术 补录 · 2026-11-14 发布 The Decoder

Runway 以 Apache 2.0 开源 Praxis-1 机器人控制模型，自测 RoboLab-120 成功率 46.2%。

事实摘要

据 the-decoder 2026 年 11 月 14 日报道，Runway 已发布 Praxis-1 机器人控制模型，以 Apache 2.0 开放权重与源代码并允许商用；模型接收相机图像、文本指令和机器人位置信息，预测环境变化并计算动作。

它先在大规模普通视频上学习物体运动与交互，再用人类动作视频和机器人数据微调，Runway 称这可能减少对昂贵机器人专用数据集的依赖。

在 NVIDIA RoboLab-120 的 120 项模拟任务中，Runway 自测成功率为 46.2%，高于同为 World Action Model 的 FLUX 3 Action 的 42.9%，但测试全部由 Runway 自行完成、尚未经独立验证。

在真实 Franka 机械臂的十项任务各十次尝试中，Praxis-1 成功 88 次、FLUX 3 Action 为 80 次；Runway 同时承认模型会混淆相似物体、难以处理模糊指令，且无法可靠自主规划长动作序列。

编辑解读

Runway 称 Praxis-1 在 9 月下旬首次推出时仅向选定合作伙伴开放，此次发布公开了权重和源代码。 标准版模型需要 80GB 显存的 GPU；

压缩版按 Runway 的估算可放入 32GB 显存的 RTX 5090，但实际峰值占用尚未实测。

Will DePue 研究/Benchmark 算力硬件与基础设施 补录 · 2026-11-13 发布 The Decoder

前OpenAI研究员称在六款中国模型权重中发现英伟达Blackwell芯片指纹。

事实摘要

前OpenAI研究员Will DePue称，其取证分析首次提供技术证据，显示DeepSeek、Moonshot AI、MiniMax和蚂蚁集团使用了受美国出口管制的英伟达Blackwell GPU。

其方法依据PyTorch初始化随机模式和不同芯片核心数差异：Hopper的H100/H800为132核，Blackwell的B200/B300为148核、GB200/GB300为152核；部分未使用词或符号的词槽保留初始随机值。

他称，2026年4月以来发布的六款中国模型带有Blackwell特征签名，而DeepSeek-V3、Kimi K2.5等更早模型显示Hopper痕迹。

按分析，DeepSeek-V4-Flash和MiniMax-M3对应148核的B200/B300，DeepSeek-V4-Pro、Kimi K3、Kimi K3.1-Pro和蚂蚁集团Ling-3.1-flash对应152核的GB200/GB300。

他估算，所分析的五个训练合计约需1.2万块Blackwell GPU，约相当于3万块较旧H100的算力。 其报告还称，Kimi K3一个训练约需4500块Blackwell处理器、耗时约70天，DeepSeek-V4-Pro约需3000块。

但他同时强调，严格来说该方法只显示哪类硬件初始化了权重，数据不揭示GPU所在地或所有者，也不能单独证明实物走私或违反美国出口法；中国企业可在中国境外数据中心租用算力。

编辑解读

若方法可复现，它可能为从模型权重侧推断训练硬件、辅助出口管制调查提供新取证路径；但现阶段仍是单一研究者声明，指纹与违法使用之间没有直接因果。

Amazon Bedrock AgentCore runtime Agent/开发者基础设施 Agent 技术 补录 · 2026-11-13 发布 aws

Amazon Bedrock AgentCore runtime V2 用一次构建快照替代逐会话容器初始化，缩短并稳定会话启动时间。

事实摘要

AWS官方技术博客称，AgentCore runtime 将 platformVersion 设为“V2”后不再逐会话初始化容器，而是在创建或更新时一次性准备环境并保存快照，新会话直接恢复。 文章称V1冷启动随镜像大小增长；

V2恢复时进程内存与已建客户端原样回来，但镜像文件按块惰性加载，文件缓存已在冻结前清空，初始化阶段的文件读取不会让恢复后的会话直接受益。

对2秒仍太慢的聊天和语音场景，文章给出四类模式：把初始化移到app.run()前、用build hook预加载大文件/CLI/浏览器、在用户打开应用或聊天窗口时后台预热，并提醒创建或更新因生成快照需数分钟。

编辑解读

这次优化的本质是把冷启动成本从每次会话前移到构建阶段；依赖大镜像、浏览器或CLI的Agent应把静态对象和常驻进程放进初始化，否则新会话仍付首次读取成本。 代价是快照随驻留内存变大、每会话按占用内存计费，且创建/更新不再即时；

应先用OverheadLatency和客户端计时确认收益。

AWS Agent/开发者基础设施 Agent 技术 补录 · 2026-11-13 发布 aws

AWS 发布非生产示例：用 LiteLLM 与 NVIDIA NeMo Switchyard 在 Amazon Bedrock 上为编码 Agent 路由模型。

事实摘要

AWS 在机器学习博客中给出示例：用 AWS CDK 在 ECS Fargate 上部署 LiteLLM 与 NVIDIA NeMo Switchyard 路由插件，让编码 Agent 的请求在 Amazon Bedrock 的模型之间分流。

示例以 Claude Opus 5.5 与 NVIDIA Nemotron 3 Super 120B 为两个候选，Stage 策略读取请求历史中最近的工具活动与结果，在两者间择一，且不调用评审模型。

文章主张按“每个解决任务成本”评估路由，即总成本除以测试通过的运行数，而不是只看每 token 价格。

该示例安装 switchyard-server 0.3.0 并运行 LiteLLM v1.102.0 镜像，NVIDIA 将其标注为演示与评估组件，代码为非生产用途。

编辑解读

示例的策略边界很窄：Stage 只支持恰好两个候选，分类器驱动的 Task、Composite 路由在该集成中不可用，因此它更像是评估脚手架而非可直接上线的网关方案。
